Rule definitions:

sql_injection:

Include a candidate when a value is inserted directly into an SQL query using:

* f-strings
* string concatenation
* percent formatting
* str.format()

Do not include parameterized queries.

Dynamic SQL identifiers selected exclusively from a fixed allowlist are safe and must not be included.

For diff review, include SQL injection when the change appears to introduce unsafe SQL construction or make an existing SQL construction newly depend on an unsafe value.

Do not include SQL injection when it is clear from the diff that the exact same unsafe SQL construction already existed before the change and the change is unrelated to it.

shell_injection:

Include a candidate when a value is inserted into a shell command executed using:

* os.system()
* subprocess.run(..., shell=True)
* subprocess.Popen(..., shell=True)
* similar shell-based execution

Do not include subprocess commands passed as an argument list without shell=True.

Commands selected exclusively from a fixed allowlist are safe.

For diff review, include shell injection when the change appears to introduce unsafe shell command construction or make an existing shell command newly depend on an unsafe value.

Do not include shell injection when it is clear from the diff that the exact same unsafe shell command already existed before the change and the change is unrelated to it.

path_traversal:

Include a candidate when a path value can access a location outside an intended base directory.

This includes:

* parent-directory traversal such as ../
* unsafe path joins
* absolute paths that override the intended base directory
* paths used without resolving and checking containment

In pathlib, joining a base Path with an absolute path discards the base path.

For example:

```python
Path("/safe/config") / "/etc/passwd"
```

produces:

```text
/etc/passwd
```

Do not include path traversal when:

* the path is resolved and verified to remain inside the intended base directory
* the filename is selected from a strict allowlist

mutable_default_argument:

Include a candidate only when a mutable object is used directly as a function default argument.

Mutable defaults include:

* list
* dict
* set

A default of None followed by creating a new list, dict, or set inside the function is safe.

Immutable defaults such as tuples are also safe.

unreachable_code:

Include a candidate when code can never execute because control flow always exits before reaching it.

This includes code after:

* an unconditional return
* an unconditional raise
* a conditional where every possible branch returns or raises before subsequent code

Do not include:

* code after a conditional return when another execution path can continue
* normal statements that remain reachable
* code that is merely unlikely to execute

duplicate_code:

Include a candidate when substantially identical implementation logic appears in multiple places and extracting that logic into a shared helper would remove meaningful duplication.

The duplicated logic should involve multiple operations or decisions, not merely similar structure.

The duplicated blocks do not need to be textually identical when they perform substantially the same sequence of validation, transformation, decisions, calculations, or result construction.

Do not include:

* thin wrapper functions that call the same shared helper
* trivial repeated assignments
* a few similar lines
* common control flow
* small similarities that would not justify extraction

long_function:

Include a candidate when one function performs several distinct responsibilities and splitting those responsibilities into focused helper functions would clearly improve readability and maintainability.

Distinct responsibilities may include:

* validating inputs or required fields
* transforming or aggregating data
* applying business rules or decisions
* performing nested iteration or non-trivial calculations
* constructing a result or output structure

A function may qualify even if it is not extremely long in line count.

Consider the number of distinct responsibilities and the complexity of the implementation, not only physical line count.

Do not include:

* a function only because it contains several lines
* a function that performs one focused responsibility with straightforward logic

list_membership_in_loop:

Include a candidate only when an in or not in membership check is repeatedly performed against a list inside a loop.

This can create quadratic behavior when both collections grow.

Example:

```python
for username in usernames:
    if username in existing_users:
        ...
```

Recommend converting the lookup collection to a set.

Do not include:

* set membership checks
* dictionary membership checks
* dictionary .get() lookups
* membership checks outside loops

string_concatenation_in_loop:

Include a candidate when a string is repeatedly extended inside a loop using += or equivalent string concatenation.

Example:

```python
result = ""

for value in values:
    result += value
```

Recommend collecting fragments and using str.join().

Do not include a single string concatenation outside a loop.
