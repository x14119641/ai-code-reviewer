Rule definitions:

sql_injection:

Report when a value is inserted directly into an SQL query using:

* f-strings
* string concatenation
* percent formatting
* str.format()

Do not report parameterized queries.

Dynamic SQL identifiers selected exclusively from a fixed allowlist are safe and must not be reported.

shell_injection:

Report when a value is inserted into a shell command executed using:

* os.system()
* subprocess.run(..., shell=True)
* subprocess.Popen(..., shell=True)
* similar shell-based execution

Do not report subprocess commands passed as an argument list without shell=True.

Commands selected exclusively from a fixed allowlist are safe.

path_traversal:

Report when a path value can access a location outside an intended base directory.

This includes:

* parent-directory traversal such as ../
* unsafe path joins
* absolute paths that override the intended base directory
* paths used without resolving and checking containment

In pathlib, joining a base Path with an absolute path discards the base path.

For example:

Path("/safe/config") / "/etc/passwd"

produces:

/etc/passwd

Do not report path traversal when:

* the path is resolved and verified to remain inside the intended base directory
* the filename is selected from a strict allowlist

mutable_default_argument:

Report only when a mutable object is used directly as a function default argument.

Mutable defaults include:

* list
* dict
* set

A default of None followed by creating a new list, dict, or set inside the function is safe.

Immutable defaults such as tuples are also safe.

duplicate_code:

Report when substantially identical implementation logic appears in multiple places and extracting that logic into a shared helper would remove meaningful duplication.

The duplicated logic should involve multiple operations or decisions, not merely similar structure.

Do not report:

* thin wrapper functions that call the same shared helper
* trivial repeated assignments
* a few similar lines
* common control flow
* small similarities that do not justify extraction

long_function:

Report when one function performs several distinct responsibilities and splitting those responsibilities into focused helper functions would clearly improve readability and maintainability.

Distinct responsibilities may include:

* validating inputs or required fields
* transforming or aggregating data
* applying business rules or decisions
* performing nested iteration or non-trivial calculations
* constructing a result or output structure

A function may qualify even if it is not extremely long in line count.

Do not report:

* a function only because it contains several lines
* a function that performs one focused responsibility with straightforward logic

list_membership_in_loop:

Report only when an in or not in membership check is repeatedly performed against a list inside a loop.

This can create quadratic behavior when both collections grow.

Example:

for username in usernames:
if username in existing_users:
...

Recommend converting the lookup collection to a set.

Do not report:

* set membership checks
* dictionary membership checks
* dictionary .get() lookups
* membership checks outside loops

string_concatenation_in_loop:

Report when a string is repeatedly extended inside a loop using += or equivalent string concatenation.

Example:

result = ""

for value in values:
result += value

Recommend collecting fragments and using str.join().

Do not report a single string concatenation outside a loop.
